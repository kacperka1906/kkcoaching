# KK Coaching reviews — isolated V3 preview

Routes: `/reviews-widget-preview/` and `/pl/reviews-widget-preview/`. Each renders exactly one widget, uses `noindex, nofollow`, and is excluded from the sitemap. The routes do not use the production layout, Footer, analytics, or navigation. Existing homepage/Footer/review enablement remain unchanged. Do not merge or deploy production in this phase.

## Files and configuration

- `AllInOneReviews.astro`: selects approved local records, applies filtering/sorting, builds source counts, and composes shared cards.
- `ReviewCard.astro`: avatar fallback, original quote, recommendation or legitimate rating, date, optional source link, and disclosure button.
- `review-controller.ts`: native scroll-snap navigation, live position/progress, source filters, expansion, image failure fallback, resize handling, reduced motion, and stable session random order. No auto-rotation.
- `review-utils.ts`: filtering, sorting, safe links, legitimate rating and source-summary calculations.
- `review-types.ts` / `review-providers.ts`: normalized data and provider contracts; the local adapter is the only implemented ingestion path. All providers are disconnected. Google/WhatsApp are disabled placeholders.
- `../../data/reviews/reviews.json`: five complete original quotes, supplied avatars, screenshot provenance. Review text is never translated. Screenshots only show day/month; dates remain null rather than inventing a year. Facebook ratings stay null.
- `../../data/reviews/reviews-config.json`: presentation defaults. Every option is implemented. `writeReviewUrl: null` uses the Facebook Page URL already configured in `admin-v2.json`; this is a Page destination, not an invented individual-review URL. If neither URL is configured, the CTA is omitted. Future provider-specific destinations can be passed through config.
- `ReviewsPreview.astro`: isolated shell with EN/PL links and a layout selector that changes the existing instance. Preview always starts in site theme.

Example usage:

```astro
<AllInOneReviews lang="en" id="client-reviews"
  config={{ layout: 'grid', theme: 'dark', sort: 'newest' }}
  filters={{ featuredOnly: true, hideEmpty: true }} />
```

Use a unique `id` when mounting multiple instances on other future pages. This preview intentionally mounts one. Desktop columns, tablet columns, mobile width, clamp lines, and visibility flags are local configuration. Full mode keeps complete text visible. Light/dark themes are supported; site theme uses the site's graphite/red/steel variables with equivalent fallbacks and the existing system-font stack.

## Content and safety

Only `enabled === true && approved === true` records are visible. WhatsApp additionally requires `consentConfirmed === true`; missing approval or consent fails closed. Source tabs and summaries are derived after filtering. Rating thresholds exclude unrated recommendations. Facebook never renders stars, even if someone accidentally adds a rating. Aggregate values only use valid 1–5 ratings from rating-based sources. No fake verification badges.

The five avatar files are exact copies of the supplied crops. Avatar preference: `sourceMeta.providerAvatar` (future) → local `avatar` → initials; loading errors follow the same fallback chain. Source screenshots stay in the supplied package, not the public gallery. Optional dates and per-review links appear only when supplied. No API requests, credentials, external widget, external font, iframe, backend, collection form, or schema were added.

Random order is seeded once per browser session using sessionStorage (with an in-memory fallback when storage is unavailable). It is not regenerated by filtering, expansion or resizing. JavaScript-disabled visitors retain full original quotes and native horizontal scrolling.

## Add a review

1. Add an approved avatar under `public/images/reviews/` (or omit it for initials).
2. Add a unique record to `src/data/reviews/reviews.json`.
3. Choose `source` and paste the complete original `quote` and reviewer display name.
4. Add only legitimate rating/date/review URL metadata. Keep Facebook `rating: null`.
5. Set `enabled`, `featured`, `approved`; WhatsApp also needs explicit `consentConfirmed: true`.
6. Build, test and publish a Deploy Preview for review. Production activation/deployment requires a separate decision outside this phase.

## Validation

```sh
npm ci
npm run build
node scripts/test-reviews-widget.mjs
```

The normal build includes SEO and promotion audits. The focused test covers consent gates, filters, sorting, rating legitimacy, unique records, preview instance count, noindex, sitemap exclusion and homepage isolation. Browser QA covers EN/PL at 360, 390, 430, 768, 1280 and 1440px, expansion/collapse, arrows/edges, Home/End/arrow keys, source filters, all three layouts, touch swipe, resizing and broken-image fallback.

Existing repository caveats: the SEO audit uses URL.pathname as a filesystem path, which fails on Windows (`C:\\C:\\...`). Local validation used an uncommitted in-memory `fileURLToPath` substitution; the original audit file is unchanged. CI/Netlify run the normal command on Linux. The audit has an existing `/pl/services` title-length warning. The normal admin-sync step also rewrites tracked generated files; those unrelated changes must not be committed. The existing dependency lock reports security advisories; dependency upgrades are outside this widget-only change.

## Phase 2 — contracts only

Implement server-side adapters against `ReviewProvider`. Facebook normalization supplies recommendation/name/text/avatar/date/IDs/URLs, preserving local fallback records on failure. Google Business Profile stays disabled until validation and authorization are ready. WhatsApp ingestion must go through an approval inbox with explicit consent before records can enter the published dataset.

A future server-side sync service will own `ReviewProviderState.lastSync`, `lastAttempt`, status/errors, persisted normalized data and `ReviewSyncService.manualRefresh`. Cache successful results, refresh at most daily, and serve the cached snapshot to visitors. Add scheduling, storage, authentication, credentials and API integrations only in that separately authorized phase. This change implements none of them.
